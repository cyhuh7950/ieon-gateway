- 상태: **설계 확정안 · 구현 승인 전.** 신산님이 확인하면 WORK_PLAN에 단계를 올리고 M0부터 구현한다.
- 작성: 2026-11-05 · 요청: 신산님 · 근거: 2026-11-05 인터뷰(9절) · 관련: [DESIGN](DESIGN.md), [NEW_SESSIONS](NEW_SESSIONS.md), [메신저 설명서](../MESSENGER_MANUAL.md)

## 1. 목표

1. **같은 메신저에서 봇 여러 개를 동시에 운영한다**(텔레그램·디스코드·슬랙). 어떤 용도로 봇을 나눌지는 사용자가 정한다. 이어온은 봇마다 허용 사용자, 볼 수 있는 세션, 대화방 연결을 따로 관리하는 틀만 제공한다.
2. **Teams를 연결한다**(개인 Microsoft 계정, Teams 무료). 연결 방식은 여러 봇과 같은 구조로 만든다.
3. **카카오톡**은 설계에 포함하되 **구현은 승인 후**에 한다(채널 개설·콜백 승인 필요).

진행 순서: 여러 봇(M0~M3) → 공개 수신 중계(M4) → Teams(M5) → 카카오톡(M6, 승인 후).

## 2. 지금 하나만 되는 이유(바꿀 곳)

| 위치 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| `messenger/main.mjs` | `.env`에서 메신저마다 정해진 이름의 토큰 하나만 읽어 봇 하나를 켬 | 웹에 정의된 봇 목록과 `.env`의 규칙 이름 토큰으로 봇마다 연결을 띄움 |
| `rooms.json` | 키 `<메신저>:<대화방>` | 키 `<메신저>:<봇ID>:<대화방>[:<주제>]` |
| 허용 사용자 | 메신저 단위 `allowedUsers` | 공통(`config.json`) + 봇별 추가(웹) |
| 서버 토큰 | 모든 봇이 `app_messenger` 하나 | 메신저 토큰은 하나 그대로, 요청마다 봇 ID를 붙여 서버가 `app_bot_<메신저>_<봇ID>`로 처리 |

## 3. 봇 정의: 토큰은 `.env`, 나머지는 웹 화면

**봇 토큰만 `.env`에 규칙 이름으로 넣고, 봇 목록·이름·역할 같은 나머지 정의는 모두 웹 화면에서 한다.** 웹 화면은 토큰을 받지도 보여 주지도 않는다.

### 3-1. 토큰 변수 이름 규칙(`.local\.env`)

봇 ID에서 변수 이름이 저절로 정해진다. 설정에 변수 이름을 따로 적지 않는다.

| 메신저 | 규칙 | 예(봇 ID `review`) |
| --- | --- | --- |
| 텔레그램 | `TELEGRAM_BOT_<ID>_TOKEN` | `TELEGRAM_BOT_REVIEW_TOKEN` |
| 디스코드 | `DISCORD_BOT_<ID>_TOKEN` | `DISCORD_BOT_REVIEW_TOKEN` |
| 슬랙 | `SLACK_BOT_<ID>_APP_TOKEN`, `SLACK_BOT_<ID>_BOT_TOKEN` | `SLACK_BOT_REVIEW_APP_TOKEN` |
| Teams | `TEAMS_BOT_<ID>_APP_ID`, `TEAMS_BOT_<ID>_APP_PASSWORD` | `TEAMS_BOT_REVIEW_APP_ID` |

- `<ID>`는 봇 ID를 대문자로, `-`를 `_`로 바꾼 것(`code-review` → `CODE_REVIEW`).
- 봇 ID: 영문 소문자·숫자·`-` 2~32자, 같은 메신저 안에서 중복 불가. 한 번 정하면 바꾸지 않는다(토큰 이름·대화방 연결·서버 앱 ID에 쓰임).
- 지금 쓰는 봇은 `default` 봇이고 기존 이름(`TELEGRAM_BOT_TOKEN`, `DISCORD_BOT_TOKEN`, `SLACK_APP_TOKEN`·`SLACK_BOT_TOKEN`)을 그대로 인정한다. 지금 `.env`는 바꾸지 않아도 된다.
- 같은 토큰 값이 두 봇에 들어 있으면 시작할 때 둘 다 켜지 않고 알린다(메신저가 같은 토큰의 동시 수신을 막거나 메시지를 나눠 보냄).

### 3-2. 웹 화면에서 정의하는 것

웹 화면에 **봇 관리**를 둔다. 웹 사용자(`app_web`)만 쓸 수 있고, 메신저·내 프로그램에서는 바꿀 수 없다. 정의는 이어온 서버 DB에 저장한다.

**역할 목록**(먼저 만들고 봇이 고른다. 같은 역할을 여러 메신저 봇이 함께 쓸 수 있다)

| 항목 | 예 | 쓰임 |
| --- | --- | --- |
| 역할 이름 | `코드 리뷰` | 표시 |
| 설명 | `PR 검토와 코드 품질 질문 담당` | 표시(`/whoami`·`/help`·웹) |
| 만들 수 있는 엔진 | Codex·Claude 중 선택 | 이 역할 봇의 `/new` 제한 |
| 허용 권한 | `read_only`·`workspace` 중 선택(`full`은 지금처럼 설정 파일에서만) | 이 역할 봇의 `/new` 권한 제한·기본값 |
| AI 역할 안내 | `너는 코드 리뷰 담당이다. 변경점의 위험과 테스트 누락을 먼저 본다.` | 이 역할 봇에서 `/new`로 만든 새 세션에 붙임(4-1) |
| 기본 세션 | `c_codex_review` 또는 없음 | 새 대화방에서 `/use` 없이 자동 연결(5절) |

**봇 목록**

| 항목 | 예 | 쓰임 |
| --- | --- | --- |
| 봇 ID | `review` | 토큰 변수 이름·서버 앱 ID(`app_bot_telegram_review`)·대화방 연결 키 |
| 메신저 | 텔레그램 | 어느 메신저 봇인지 |
| 이름 | `코드 리뷰 봇` | 이어온에서만 쓰는 표시 이름(한글 가능). 메신저 쪽 이름(BotFather의 name, `@…bot`으로 끝나는 username)은 신산님이 직접 정하고, 이어온은 시작할 때 실제 이름·username을 읽어 함께 보여 준다 |
| 부르는 이름 | `리뷰`, `리뷰봇` | 대화방에서 사람이 이 봇을 부를 때 쓰는 이름(한글 가능, 여러 개). 5절 |
| 역할 | `코드 리뷰` | 3-2 역할 목록에서 고름 |
| 추가 허용 사용자 | `123456789` | 공통 허용 사용자에 더함 |
| 켜기/끄기 | 켬 | 끄면 메신저 프로세스가 그 봇을 띄우지 않음 |
| 상태(읽기 전용) | 토큰 있음·연결됨·실제 봇 이름 | 메신저 프로세스가 보고. `.env`에 규칙 이름의 토큰이 없으면 "토큰 없음 — `.env`에 `TELEGRAM_BOT_REVIEW_TOKEN` 추가"로 안내 |

- 봇 수 제한은 두지 않는다.
- 봇을 추가·수정·끄면 메신저 프로세스가 1분 안에 다시 읽어 적용한다(새 토큰을 `.env`에 넣은 경우에는 `messenger`를 다시 켠다).
- 봇을 지우면 그 봇의 대화방 연결이 지워진다. 그 봇이 만든 새 세션은 웹에서 계속 보인다.

### 3-3. 메신저 프로세스와 서버 인증

**M0 API:** 웹 사용자만 `GET /v1/admin/roles`·`PUT|DELETE /v1/admin/roles/{역할ID}`·`GET /v1/admin/bots`(상태 포함)·`PUT|DELETE /v1/admin/bots/{메신저}/{봇ID}`. 메신저 프로세스(봇 헤더 없이 메신저 토큰)만 `GET /v1/messenger/bots`(켜진 봇 정의·역할)·`POST /v1/messenger/bots/status`(상태 보고, 토큰 값은 받지 않음). default 봇은 지울 수 없다. 역할 권한은 `read_only`·`workspace`만(`full`은 거절). 쓰는 봇이 있는 역할은 지울 수 없다.


봇마다 서버 토큰 파일을 따로 만들지 않는다. 메신저 프로세스는 지금의 메신저 토큰(`app_messenger`)으로 서버에 접속하고, 요청마다 어느 봇인지(`x-ieon-bot: review`)를 붙인다. 서버는 그 봇이 웹에 정의돼 있고 켜져 있을 때만 그 요청을 `app_bot_telegram_review`로 처리한다. 정의되지 않은 봇 이름은 거절한다. 메신저 토큰은 처음부터 메신저 전체를 대표하므로 권한이 넓어지지 않는다.

### 3-4. 기존 설정 자동 전환

웹에 봇이 하나도 없으면 지금처럼 동작한다. `.env`에 기존 이름의 토큰이 있는 메신저는 `default` 봇(이름 "기본 봇", 역할 없음)으로 처음 시작할 때 자동 등록하고, 서버 앱 ID는 기존 `app_messenger`를 그대로 쓴다. `rooms.json`의 옛 키 `<메신저>:<대화방>`는 처음 읽을 때 `<메신저>:default:<대화방>`로 바꿔 저장한다. **아무것도 바꾸지 않아도 지금과 같이 동작한다.**

## 4. 세션 범위(봇별 서버 앱 ID)

> 앱 ID는 `app_bot_<메신저>_<봇ID>`다(M0에서 확정). 봇 ID는 메신저마다 따로라 같은 `ieun01`이 텔레그램·디스코드·슬랙에 있어도 서로 다른 봇·다른 앱으로 본다.

봇마다 서버 앱 ID를 따로 두고, 세션 `bindings[].appIds`(기존 세션) 또는 새 세션 등록 시 정해지는 `appIds`로 어느 봇이 볼 수 있는지 정한다. 웹·메신저·내 프로그램을 구분하는 지금 방식을 그대로 쓴다.

| 세션 | 보이는 곳 |
| --- | --- |
| 기존 세션 연결(사람이 `server.json`에 등록) | `appIds`에 적은 앱. 봇에 보이게 하려면 `app_bot_<메신저>_<id>`를 넣는다(`default` 봇은 기존 `app_messenger`) |
| 봇에서 `/new`로 만든 새 세션 | **만든 봇 + 웹**(`app_bot_<메신저>_<id>`, `app_web`) |
| 웹에서 만든 새 세션 | 웹 + `new-sessions.json` `creatorApps`의 메신저 앱(지금과 같음) |

- 새 세션 `creatorApps`에 봇 앱 ID를 하나씩 적지 않아도 되게, `creatorApps`에 `"app_bot_*"`(모든 봇) 표기를 허용한다.
- 다른 봇에서 만든 세션은 `/sessions`에 나오지 않고, 이름으로 `/sleep`·`/close`해도 "없음"으로 나온다.
- 기존 세션을 봇에 보이게 하는 설정(`appIds`)도 웹 봇 관리 화면에서 고른다(봇마다 "볼 수 있는 기존 세션" 선택). 저장은 지금처럼 서버가 한다.

### 4-1. 역할이 동작에 미치는 영향

| 역할 설정 | 동작 |
| --- | --- |
| 만들 수 있는 엔진 | 그 봇에서 `/new`로 다른 엔진을 고르면 거절("이 봇은 Codex만 만들 수 있음") |
| 허용 권한 | 범위 밖 권한을 고르면 거절. 권한을 안 고르면 역할의 첫 번째 허용 권한 |
| AI 역할 안내 | 그 봇에서 `/new`로 만든 새 세션의 **첫 질문 앞에** 역할 안내를 붙여 보낸다. 같은 세션의 다음 질문은 앞 대화를 이어 쓰므로 다시 붙이지 않는다. 기존 세션 연결(사람이 쓰던 세션)에는 붙이지 않는다. 붙인 안내는 이어온 기록에서 질문과 구분해 보여 준다 |
| 기본 세션 | 연결이 없는 대화방에서 첫 메시지를 받으면 그 세션에 자동 연결하고 "기본 세션 ○○에 연결함"을 알린다. 그 봇이 볼 수 없는 세션이면 자동 연결하지 않는다 |
| 표시 | `/whoami`·`/help` 첫 줄에 "봇 이름 · 역할 · 설명", 웹 봇 목록·세션 화면에 표시 |


## 5. 대화방 동작

- **연결은 봇마다 따로** 저장한다. 같은 그룹에 봇 A·B가 있으면 A는 세션 X, B는 세션 Y에 연결할 수 있다.
- **그룹·채널에서는 부른 봇만 답한다.** 부르기:
  - **부르는 이름**으로 시작: `리뷰, 이 PR 봐 줘` · `리뷰: …` · `리뷰야 …` · `@리뷰 …`(메시지 맨 앞의 부르는 이름 뒤에 쉼표·쌍점·공백·"야/아"가 오면 그 봇. 부르는 이름은 떼고 나머지를 질문으로 보냄)
  - `@봇` 멘션
  - 그 봇이 보낸 메시지에 답장
  - 텔레그램 `/명령@봇username`
  - 명령도 부르는 이름으로: `리뷰 /status` · `리뷰, /new codex x`
- **구현 메모(M2):** 부르는 이름이 없으면 봇 ID로 부를 수 있다(예: `ieun01, /whoami`). 그 방에서 세션에 연결된 우리 봇이 이 봇뿐이거나 아무도 없으면 부르지 않아도 받는다(아무도 연결 안 된 방에서는 두 봇이 함께 답할 수 있으니, 먼저 부르는 이름·멘션으로 `/use`한다). 역할의 기본 세션 자동 연결은 `/help`·`/sessions`·`/use`·`/new`에는 적용하지 않는다.
- 그 방에 우리 봇이 **하나뿐이면** 지금처럼 부르지 않아도 받는다. 봇은 같은 방의 다른 우리 봇을 알 수 없으므로, "하나뿐"은 그 방에서 연결(`/use`·`/new`)된 우리 봇이 하나인지로 판단한다(같은 메신저의 모든 봇이 한 프로세스라 `rooms.json`으로 확인 가능).
- **1:1 대화**는 그 봇이 항상 답한다. 부르는 이름을 붙여도 떼고 처리한다.
- **부르는 이름 규칙**(웹에서 관리): 봇마다 1개 이상, 1~20자, 한글·영문·숫자. 같은 메신저의 봇끼리 겹치면 저장을 거절한다(대소문자·공백 무시). 명령어와 같은 이름(`help`, `new` 등)은 쓸 수 없다. 없으면 봇 ID를 부르는 이름으로 쓴다.
- **메신저 제약**: 텔레그램 그룹에서는 봇이 기본적으로 명령·멘션·답장만 받는다(privacy mode). 부르는 이름으로 부르려면 BotFather `/setprivacy` → Disable이 필요하다. 웹 봇 상태에 "그룹 일반 글 수신 꺼짐 — 부르는 이름이 동작하지 않음"을 보여 준다(텔레그램 `getMe`의 can_read_all_group_messages). 디스코드는 Message Content Intent, 슬랙은 해당 채널 `message.*` 이벤트가 켜져 있어야 한다.
- 연결이 없는 대화방은 역할의 **기본 세션**이 있으면 그 세션에 자동 연결한다(4-1).
- `/whoami`는 봇 ID와 서버 앱 ID도 보여 준다.

## 6. Teams·카카오톡 공개 수신 중계(M4)

Teams와 카카오톡은 메신저 쪽이 **공개 HTTPS 주소로 메시지를 보내는** 방식이다. 이 PC는 지금처럼 공개 포트를 열지 않는다.

```
Teams(Azure Bot) / 카카오 오픈빌더 ──HTTPS──▶ Oracle 중계(ieon-gateway.sinsan.kr)
                                                  ▲ 대기 중 메시지 보관(짧게), 서명 검증
                                                  │ PC가 먼저 접속(긴 대기 폴링·웹소켓)해 가져감
                                          SINSAN PC 메신저 봇 프로세스 → 이어온 서버
```

- 중계는 **메시지 전달만** 한다. 질문 원문은 PC가 가져가면 바로 지우고 로그에 남기지 않는다. 이어온 서버·DB·토큰은 PC에 그대로 둔다.
- 메신저 서명 검증(Teams Bot Framework JWT, 카카오 스킬 요청 확인)은 중계에서 하고, 중계↔PC는 별도 토큰으로 인증한다.
- PC가 꺼져 있으면 중계가 "PC 연결 끊김"으로 바로 답한다(카카오 5초 제한).
- Oracle `ieon-gateway.sinsan.kr`(A 레코드 확인됨)에 TLS·reverse proxy를 둔다. **Oracle 배포·포트·방화벽 변경은 후보와 되돌리는 방법을 제시하고 별도 승인 후 진행한다.**

## 7. Teams(M5)

- 개인 Microsoft 계정(Teams 무료)에서 쓴다. Azure에 Bot 리소스를 만들고 Teams 채널을 켠다. 메시지 수신 주소는 6절 중계.
- 봇은 웹 봇 관리에서 메신저 Teams로 등록하고, 앱 ID·비밀번호는 `.env`의 `TEAMS_BOT_<ID>_APP_ID`·`TEAMS_BOT_<ID>_APP_PASSWORD`에 둔다. 봇별 범위·대화방 동작은 4·5절과 같다.
- **확인 필요(M5 시작 전):** 개인용 Teams에서 사용자 지정 봇을 대화에 추가하는 것이 허용되는지(조직용 Teams처럼 앱 업로드가 되는지). 안 되면 Teams 범위를 다시 정한다. 신산님이 이전에 한 Teams 연결 시험 방법을 이때 확인한다.
- Azure 계정·Bot 등록·비밀번호 발급은 신산님이 직접 한다.

## 8. 카카오톡(M6, 승인 후)

- 카카오톡 채널(비즈니스 채널)을 개설하고 카카오 i 오픈빌더에서 봇을 만들어 스킬 서버로 6절 중계를 등록한다.
- 스킬 요청에는 **5초 안에** 답해야 하므로, AI 답은 **콜백(AI 챗봇 콜백) 기능**으로 나중에 보낸다. 콜백은 오픈빌더 신청·승인이 필요하다. 승인 전에는 "접수됨"만 바로 답하고 결과는 "/status"로 확인하는 방식이 가능하다.
- 사용자 구분은 카카오가 주는 봇 사용자 키로 하고, 허용 사용자는 `/whoami`로 확인해 등록한다.
- **구현은 채널 개설·콜백 승인 후 신산님 승인을 받고 시작한다.**
