# 이어온 관리 App Server — 실현 가능성과 원래 요구 대비 검토

- 기록: 2026-10-29 17:40 KST / 담당 어울.
- 상태: **대안 검토서·방향 미결정. 승인 설계/구현 계획이 아니다.**
- 범위: 이어온이 직접 관리하는 공식 Codex App Server의 가능성, 기존 요구와 차이, 인증·호스팅 조건, 사용할 화면.
- 이번 작업: 공개 공식 문서와 기존 실증 기록만 검토했다. 코드/화면 구현·서버 기동·로그인·모델·키 등록·배포는 하지 않았다.

## 1. 판정

**이어온이 소유하는 App Server와 그 저장소의 대화를 생성하고 같은 ID로 이어가는 구조는 공식 프로토콜로 설계할 수 있다.** 실제 제품 구현/재시작 복구/모델 응답 성공을 확인한 판정은 아니다.

이어온의 여러 화면이 한 실행 주체를 사용하면 각 화면이 별도 writer를 얻을 필요가 없다. 같은 대화 요청은 이어온에서 직렬화한다. 그래도 App Server 프로토콜만으로 앱·이용자 권한, 요청 중복/결과불명 복구가 완성되는 것은 아니며 기존 승인 계약의 보호 장치를 구현·검증해야 한다. [공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)

이 방식은 원래 요구인 **다른 PC에 이미 있는 특정 Codex 대화를 그 ID로 그대로 이어쓰기**의 해결 확인과 다르다. 방향 선택 전 기존 요구를 없애거나 신규 대화로 달성했다고 처리하지 않는다.

## 2. 기존 결과를 어떻게 사용하는가

- 이전 별도 계정 실증은 official login 성공, CLI Codex Cloud 목록0개, 지정 ID NOT_FOUND였다. 본문·실제 답변·P0/P1은 미실행이었다. 모든 대화가 없거나 연결이 불가능하다는 결론은 아니다. [실제 결과](../validation/CLOUD_ACCOUNT_ACCESS_RESULT.md)
- 다른 업무 대상의 로컬 OS 잠금은 그 대상의 별도 writer 충돌 관찰이다. 여러 기기의 같은 계정 로그인 자체나 새 클라우드 시험 대상의 잠금을 입증한 결과가 아니다.
- 이번 대안은 해당 문제를 강제 해제하거나 원본을 이동하는 우회가 아니다. 업무 Desktop의 CODEX_HOME·인증·원래 thread를 공유하지 않는 독립 저장소와 실행 주체를 제안한다.

## 3. 원래 요구와 달라지는 부분

| 항목 | 원래 요구 | 관리 App Server 대안 |
| --- | --- | --- |
| 대화 출발점 | 다른 PC에서 이미 사용 중인 기존 대화 | 기본은 이어온이 만든 전용 대화 |
| ID 재사용 | 원래 Desktop/클라우드 ID가 같아야 함 | 관리 저장소에서 발급받은 ID를 계속 재사용 |
| 기존 기록 | 원래 PC/서비스의 과거 기록이 필요 | 전용 저장소에 없는 원래 기록은 자동으로 가져오지 않음 |
| 로그인 | 다른 계정에서도 원래 대화에 연결 가능한지 실증 | 모델 인증과 이어온 대화 접근 권한을 별도 관리. 계정 변경이 대화 소유권 이전이 아님 |
| 화면 교대 | 공식 Desktop→이어온→공식 Desktop | 우선 이어온 PC 웹↔모바일 웹에서 같은 관리 대화 사용 |
| Desktop 연동 | 같은 원래 thread에 양방향 반영 | 공식 Desktop이 전용 App Server를 그대로 사용하는 경로는 미확인. 동일 기능으로 약속하지 않음 |
| 충돌 관리 | 기존 Desktop/별도 runtime 사이 인계·충돌 | 이어온이 단일 writer를 소유하고 요청을 직렬화. 외부 실행기가 저장소를 직접 열지 않도록 운영 |
| 원본 보존 | 원래 Codex 대화는 변경/삭제하지 않음 | 원래 업무 저장소와 분리하므로 직접 조작하지 않음 |
| PC 장애 | 원래 PC가 끊기면 원래 대화 연결 불가 | PC 배치는 해당 PC 상태에 의존, Oracle 배치는 해당 서버 상태에 의존 |

기존 thread 재사용이 계속 필수라면 아래 어느 안도 그 요구를 충족했다고 판정할 수 없다. 기존 대화 연결은 별도의 미해결 요구로 남긴다. 이번에 선택할 수 있는 것은 **관리 대화 기능을 별도 기능으로 먼저 개발할지**다.

## 4. 인증·호스팅의 확인된 경계

### 기존 Codex의 ChatGPT 로그인

공식 문서는 기존 App Server 인증을 사용하는 local/open-source 앱의 계속 사용을 설명하면서 상용·호스팅 서비스에는 허용되지 않았다고 명시한다. **이전 개인 로그인 실증 성공을 Oracle 서비스 운영 허용으로 확대하지 않는다.** API 키의 일반적인 서버 API 사용과 이 구독 로그인 경로를 혼동하지 않는다. [Auth endpoints](https://learn.chatgpt.com/docs/app-server#auth-endpoints)

### 등록된 Sign in with ChatGPT

- 공식 문서는 앱의 사용자 로그인과 선택적 ChatGPT plan 사용을 별도 능력으로 설명한다. **둘 다 기존 ChatGPT 대화 접근 권한을 주지 않는다.**
- 현재 가이드는 오픈소스/개인 로컬 프로젝트 및 선택된 private 앱의 이용 가능성을 안내한다. commercial은 제한된 파트너 시험이다. private인 이어온이 자동 승인된다고 보지 않는다. 저장소 공개 전환으로 이 조건을 맞추자는 제안도 하지 않는다.
- 신규 앱 등록/허용 범위·계정/워크스페이스·모델 사용 자격·동의 절차를 확인해야 한다. 단순 웹 로그인 버튼이나 모델 목록 표시만으로 추론 사용 가능을 판정하지 않는다.

[공식 소개·이용 자격](https://developers.openai.com/siwc/quickstart), [로그인·사용량·대화 접근의 구분](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)

SIWC용 App Server 공식 가이드는 **앱이 정식 발급받은 OAuth 인증으로 Responses provider를 구성하고 stdio로 제어하는 경로**를 제시한다. 이는 기존 Desktop 토큰을 추출해 쓰는 방식과 다르며, 이번 설치 버전/이어온의 실제 적용·허가는 미검증이다. [App Server 연동](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

원격 VM용 공식 안내도 있으나 open-source 앱을 대상으로 보호된 신규 등록 credential의 전송을 요구한다. 이 안내만으로 private 이어온 호스팅이 승인되는 것은 아니다. 또한 현재의 credential 복사 금지와 실제 허용 범위를 별도로 결정해야 하므로 이 전송 경로를 기본안으로 채택하지 않는다. 실제 토큰 전송/등록은 하지 않는다. [Self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)

### API 키

API 키는 공식 programmatic/CI 사용 경로이며 API 조직 기준의 종량 과금이다. ChatGPT 구독 포함 사용으로 보지 않는다. 서버에서는 키를 backend의 보호된 Secret 위치에 두고 웹 화면/일반 로그/이미지로 전달하지 않는 안을 제안한다. 키 등록·비용·서버 배치는 방향 확정 후 별도 승인 범위다. raw App Server 실행을 공개·비신뢰 환경에 노출하지 않는다. [공식 인증 문서](https://learn.chatgpt.com/docs/auth)

## 5. 배치 대안

| 안 | 실행·화면 | 인증과 조건 | 장점 | 제약/판정 |
| --- | --- | --- | --- | --- |
| A. 개인 PC 전용 | 이어온이 PC의 전용 App Server를 관리. 같은 PC의 이어온 로컬 웹 화면 사용 | 개인 로컬 앱 자격·앱 등록을 확인한 SIWC/공식 구독 경로 검토. 기존 OAuth 허용을 새 앱에 무조건 적용하지 않음 | 구독 중심의 작은 개인용 시험에 적합 | PC가 켜져 있어야 함. Oracle 중계를 붙였다고 호스팅 제한이 사라지는 것은 아님. 모바일/외부 공개는 이 기본안에 포함하지 않음 |
| B. Oracle + API 키 | 서버의 전용 App Server와 영속 저장소, PC/모바일 공통 이어온 웹 | API 키·API 과금. 사용자 인증은 이어온 API가 별도 검증 | 상시 공용 모듈이라는 서비스 목표에 가장 직접적. 업무 Desktop에 의존하지 않음 | 사용료 예산/Secret/배치 승인 필요. 새 전용 대화 기준이고 기존 Desktop 기록 자동 연결은 아님 |
| C. 등록·허용된 SIWC + 원격 배치 | 허용 조건이 확인된 전용 App Server와 이어온 웹 | selected private/commercial 자격 및 호스팅·등록·credential 주입 범위 확인이 선행 | 승인된다면 사용자별 구독 사용권 활용 가능성을 검토할 수 있음 | 현재 이어온 승인/자격 미확인. 원격 VM 가이드를 private 상용 서비스 허가로 확대할 수 없음. 조건 확정 전 보류 후보 |

**권장:** Oracle에서 상시 서비스하는 목표를 우선하면 B를 제안한다. 이는 API 비용 지출 승인이나 기존 thread 요구를 포기한 결정이 아니다. 구독 사용이 우선이고 개인 PC 범위가 괜찮다면 A가 먼저다. C는 등록·허용 조건이 확인되기 전 첫 구현안으로 선택하지 않는 편을 권한다.

별도 API 키 인증을 택하더라도 실행 엔진은 공식 Codex App Server다. 모델 API의 새 conversation 서비스로 몰래 바꾸거나 처음부터 두 실행 adapter를 구현하는 안이 아니다.

## 6. 사용할 화면

**PC와 모바일에서 같은 ‘이어온 대화’ 웹 화면**을 기본 제안한다. A는 PC 로컬에서 시작하고 B/C는 보호된 HTTPS 웹으로 제공한다. 기존 정적 시안의 대화 선택·질문·상태·답변 구성을 재사용하는 방향이며 이번에 UI를 구현하거나 열지는 않았다.

화면 후보의 실제 자료는 [기존 정적 시안](assets/continuity-v1.html)이다. 현재 연결된 실행 화면이 아니며, 관리 대화용 표기/인증·과금 상태를 선택안에 맞추는 작업은 방향 확정 후 수행한다.

| 화면/영역 | 사용자에게 보여줄 내용 |
| --- | --- |
| 연결 설정 | 이어온 사용자 인증과 모델 인증을 구분. API 키는 backend 보호 위치에 주입, SIWC는 자격 확인 후 공식 로그인/사용 동의. ‘구독’/‘API 별도 과금’을 명확히 표시 |
| 상단 대화 정보 | ‘이어온 전용 대화’, 실행 위치 PC/서버, 검증한 관리 ID 일부, 모델 인증 방식·권한 확인 상태 |
| 질문·답변 | 첫 샘플은 대화 하나를 선택해 단순 질문/응답. 같은 관리 ID를 유지. 긴 답변과 모바일 키보드 스크롤 검증은 구현 후 수행 |
| 처리 상태 | 접수와 실행 완료 분리. 사용 중은 추가 실행 차단. unknown은 기존 결과 확인으로 이동하며 재전송을 기본 동작으로 두지 않음 |
| 기록 관리 | 조회·삭제 범위를 명확히 표시. 기존 업무 Codex 대화/저장소 삭제와 혼동하지 않도록 분리. 관리 App Server 원문까지의 삭제 범위는 구현 설계에서 확정 |

공식 Codex Desktop·ChatGPT 모바일 앱을 이어온의 화면으로 사용하는 연동 경로는 확인하지 못했다. 필요하면 이후 같은 이어온 웹을 감싼 작은 데스크톱 창을 검토할 수 있지만 첫 단계부터 별도 desktop/mobile 앱을 만들 필요는 없다.

‘계정 연결됨’·‘모델 목록 조회됨’과 ‘실제 답변 검증됨’은 다른 상태로 표시한다. 구독 한도 부족 시 자동 API 전환/추가 크레딧 사용/계정 교체를 하지 않는 기존 요구를 유지한다.

## 7. 개념 구성과 미검증

제안 구성: **이어온 화면 → 인증 HTTP API·권한/요청 직렬화·상태 저장 → 관리 App Server(stdio) → 외부 모델**. 전용 CODEX_HOME·작업 폴더·영속 이력과 사용자/앱/conversation↔runtime/thread 매핑을 유지한다. App Server 포트를 인터넷에 직접 열지 않는다. 모델 없는 대역 결과와 실제 모델 응답은 별도 검증한다.

- 전용 대화의 시작/재개 API가 있다는 문서 근거와 실제 영속성/재시작/중복/unknown 복구 통과를 구분한다. 사용하지 않은 thread/start 응답만으로 영속 보장을 선언하지 않는다.
- 과거 환경 조사에는 WSL x86_64, Oracle aarch64가 기록됐다. 현재 메모리/디스크 여유·ARM64 선택 버전 동작·정식 Compose/영속 저장/health는 이번에 확인하지 않았다. 배포 가능 완료 판정이 아니다.
- 읽기 전용 질의/도구 금지 또는 검색 allowlist, 사용자·앱 소유권·입출력/동시성/사용량 한도와 기존 결과 대조는 후속 설계의 필수 조건이다. App Server만 실행하면 자동으로 충족되지 않는다.
- 현재 설치 alpha 버전과 최신 SIWC 문서의 호환·모델 권한은 실증하지 않았다. 구현 시 지원 버전을 고정하고 검증한다.
- B를 선택해도 구현·검증은 로컬/WSL부터 진행하고, Oracle는 별도 승인된 exact 후보의 staging 배치 단계다. 실서버에서 바로 개발·시험을 시작하는 제안이 아니다.
- 원래 Desktop/클라우드 대화 이어쓰기·다른 계정 간 원래 ID 접근·공식 Desktop 양방향 연동은 여전히 미검증이며 이번 대안의 완료 조건에 숨겨 넣지 않는다.

## 8. 결정할 항목
