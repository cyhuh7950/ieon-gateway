# 요청 관리(RC): 승인·실행 결과 연결, 요청별 중지, 작업 화면, 재개 확인, 사람 인계

기준: 2026-11-16. 상태: **RC1 코드 완료(7절)·허브와 이 PC에 적용(2026-11-16) — 실제 엔진 확인 전. RC2 코드 완료(8절)·허브와 이 PC에 적용(2026-11-16) — 실제 엔진 확인 전. RC3 코드 완료(9절)·허브와 이 PC에 적용(2026-11-16).** RC4~RC5는 계획만. 모델 호출 0.

근거: 신산님 지시문 "이어온 담당자 작업 지시문"(OpenBot·Free Claude Code 검토 후속)과 `D:\사전 검토.txt`. 이 문서가 지시문의 "첫 회신"이다. 지시문의 링크는 다른 작업자의 `ieon-agent-bridge` 문서를 가리키지만, 신산님이 이 저장소(ieon-gateway)에서 진행하라고 지시해 이 저장소의 정본(WORK_PLAN·WORK_STATUS·설계)에 대조했다. `ieon-agent-bridge`는 읽지도 고치지도 않았다(작업계획 머리말만 확인).

## 1. 참고한 두 프로젝트(문서만 읽음, 설치·실행 안 함)

| | OpenBot (CopilotKit) | Free Claude Code |
| --- | --- | --- |
| 무엇인가 | 여러 AI에게 브라우저·파일·업무 도구를 주고 행동 전에 승인받는 업무용 에이전트 플랫폼 | 코딩 에이전트(Claude Code·Codex 등)를 여러 모델 공급자로 돌려 주는 프록시, 디스코드·텔레그램 연동과 브라우저 화면 |
| 라이선스 | 저장소 MIT(실행에 필요한 Intelligence는 별도 라이선스) | **AGPL-3.0-only** |
| 가져올 생각 | 승인 카드의 범위 구분, 사람 인계(직접 처리) 카드, 승인 뒤 실행을 감사 기록에 남기기, 봇별 승인·활동 화면 | 답장으로 **그 요청만** 중지(`/stop` 답장), 브라우저에서 세션 이어 보기 |
| 문서에 없는 것 | 요청 ID·승인 상태 이름·결정과 실행 결과를 잇는 방식, 승인 만료, 중복 응답 처리, 카드에 보이는 칸 | 요청·메시지 추적 구조, 세션 재개 동작, 승인 흐름(없음). 슬랙 미지원 |

- **소스 사용 원칙(2026-11-16 신산님 결정):** 이어온 방식으로 만들되 필요한 소스는 가져와도 된다. 이어온도 소스를 공개할 계획이라 AGPL도 괜찮다. 단, Free Claude Code(AGPL-3.0)의 코드를 넣으면 이어온도 **AGPL-3.0 조건**으로 공개해야 한다(더 느슨한 조건 불가). OpenBot(MIT)은 저작권·라이선스 표시를 남기면 된다. 가져올 때는 어떤 파일을 어디서 가져왔는지 이 문서에 적는다. **지금까지 가져온 소스는 없다**(RC1은 이어온의 W1·W2 위에 직접 만듦).
- OpenBot 문서도 "바깥 에이전트가 자기 도구를 직접 실행하면 그 도구는 OpenBot 승인 정책을 거치지 않는다"고 적는다. 이어온도 같다: **엔진이 실행 전에 물어 오는 경로가 있을 때만** 승인 카드를 보장할 수 있다.
- 사전 검토의 "기존 Codex 세션 인수는 OpenBot에서 확인되지 않음"은 이어온의 핵심(같은 세션 재사용)과 겹치지 않는다. 이어온은 그 부분을 이미 실증했다.

## 3. 엔진별 승인·중지·재개 지원 근거

| 엔진 경로 | 승인(실행 전 묻기) | 요청 중지 | 같은 세션 재개 |
| --- | --- | --- | --- |
| Codex app-server(작업 모드) | **실측 PASS**(거부·허용, `w2-work-mode-real*.json`). 실행 결과 이벤트(`item/completed`)가 오는 것은 `w0-codex-appserver-20261113.json`에서 확인 — 승인과 잇는 코드는 없음 | `turn/interrupt` 호출 코드 있음(막힌 항목용). **사용자 중지로는 미실측** | 실측 PASS(X2·N1·O6) |
| Codex SDK(번갈아 쓰기, 읽기 전용) | **불가**(W0: SDK는 승인을 넘기지 못함) → 버튼 없음 | `AbortController`로 차례 중단 코드 있음. 사용자 중지로는 미실측 | 실측 PASS(X1) |
| Claude 새 세션(`claude -p`) | **보류**(W0: 읽기 전용 명령이 승인 없이 실행됨) → 버튼 없음 | 프로세스 종료로 가능할 것. 종료 뒤 세션 상태 **미실측** | 실측 PASS(N2) |
| Claude 채널(사람이 띄운 창) | 지금처럼 터미널에서 사람이 승인 | **불가**(채널로는 실행 중인 차례를 멈출 수단이 없음). 대기 중 취소만 가능, 실행 중이면 "원래 창에서 멈추세요" 안내 | 실측 PASS(C1) |
| Grok·Antigravity(한 번 실행) | 없음 → 버튼 없음 | 프로세스 종료. 미실측(Grok은 구독 전) | Antigravity 실측 PASS, Grok 미확인 |

- 한 세션은 한 번에 질문 하나만 받는다(사용 중이면 거부). 그래서 지시문의 "A·B 중 A만 취소"는 **서로 다른 대화(또는 방의 다른 AI 직원)**에서 도는 두 요청으로 시험한다.
- 중지와 완료가 같이 오면 **먼저 확정된 쪽이 이긴다**: 이미 완료 보고가 들어온 요청은 중지할 수 없다고 답하고, 중지 요청 뒤 종료를 확인하지 못하면 "결과 불명"으로 두고 잠근다(자동 재전송 없음).

- 순서는 지시문의 우선순위대로 RC1 → RC2 → RC3 → RC4 → RC5. SV1(서버 엔진 칸)은 신산님 지시대로 이 뒤로 둔다.
- 메신저의 첫 실제 확인 채널은 슬랙. R1의 실제 메신저 확인과 함께 한다(시험 봇·모델 호출 승인).
- PC형·허브형 화면과 이어온 앱에 똑같이 넣는다. 화면은 지금의 대화 중심 구조를 그대로 쓰고 탭·스크롤을 늘리지 않는다.

## 5. RC1 최소 변경 범위

1. **저장:** `approvals`에 실행 상태(없음 → 실행 중 → 완료/실패/결과 불명)·끝난 시각·엔진 항목 ID·그때의 AI 직원 이름과 엔진을 더한다. 명령 원문 밖의 결과 내용(출력)은 저장하지 않는다(종료 코드까지만).
2. **엔진 → 서버:** app-server 차례가 허용한 항목의 `item/completed`를 보고 결과를 연결부가 서버에 알린다(`POST /v1/device/approvals/<id>/result`, 그 기기의 승인만). 차례가 끝났는데 결과가 안 왔으면 "결과 불명".
3. **화면:** 카드 한 장이 승인 대기 → 승인됨 → 실행 중 → 완료/실패/결과 불명(또는 거부·시간 지남)으로 바뀐다. 웹·앱·메신저가 같은 상태를 읽는다. 메신저에는 "승인 요청 n: 실행 완료/실패"를 원래 대화방(슬랙은 원래 스레드)에 보낸다.
4. **메신저 승인 번호 저장:** 메신저를 다시 켜도 `/허용 n`이 같은 승인을 가리키게 한다.
5. **시험(대역, 모델 0):** 거부 → 실행 0건, 허용 → 실행 1건, 같은 카드 두 번 누르기·두 화면 동시 응답 → 실행 1건, 주인 아닌 사람·만료·차례 끝 → 차단, 허용 뒤 실행 실패 → 두 화면 같은 실패, 엔진이 다른 항목으로 답하려 하면 차단, 승인 미지원 엔진에는 버튼 없음. 일부러 망가뜨려 시험이 실패하는지도 확인.
6. **하지 않는 것:** "이 대화에서 허용"·"계속 허용"(OpenBot의 넓은 범위), Claude·SDK 경로의 승인, 슬랙 누르는 버튼(지금의 답글 명령 유지 — 모든 메신저 공통).

## 6. 확인하지 못한 것

- 두 프로젝트를 설치하거나 실행해 보지 않았다(공식 저장소 문서만).
- OpenBot이 결정과 실행 결과를 어떤 구조로 잇는지는 문서에 없어 이어온 방식은 자체 설계다.
- Free Claude Code의 세션 재개 코드는 직접 읽지 않았다(사전 검토의 설명만).
- 사용자 중지의 실제 엔진 동작(app-server `turn/interrupt`, SDK 중단, `claude -p` 종료 뒤 세션 상태)은 미실측 — RC2 착수 전에 실측한다.
- 지시문이 기준으로 든 `ieon-agent-bridge`의 단계 이름과는 대조하지 않았다(다른 작업자 폴더).

## 7. RC1 구현 기록 (2026-11-16, 신산님 "우리 방식으로 진행")

- **저장(`approvals` 표에 열 추가):** 실행 상태 `exec_status`(없음 → `running` → `completed`/`failed`/`unknown`)·끝난 시각·종료 코드·엔진 항목 ID·대화별 번호 `seq`·그때의 AI 직원 이름(없으면 대화 이름)과 엔진. 출력 내용은 저장하지 않는다.
- **카드 한 장의 상태(`approvalState`):** `pending` 승인 대기 → `approved` 승인됨(엔진에 전달 전) → `running` 실행 중 → `completed` 완료 / `failed` 실패 / `unknown` 결과 불명. 실행하지 않은 쪽은 `denied`·`expired`·`turn_ended`.
- **엔진 → 서버:** Codex app-server 승인 요청의 항목 ID(`itemId`, 프로토콜에서 필수 — 0.165.0 스키마를 로컬로 뽑아 확인)를 승인에 적어 두고, 그 항목의 `item/completed`(상태 `completed`/`failed`, 명령은 종료 코드)를 연결부가 `POST /v1/device/approvals/<id>/result`로 알린다. **항목 ID가 정확히 같은 것만** 잇는다(순서로 짐작하지 않음 — 작업 모드에서도 승인 없이 실행되는 읽기 전용 명령이 있어서). 종료 코드가 0이 아니면 실패. 권한 추가는 실행 항목이 없어 허용 전달이 곧 완료.
- **서버가 막는 것:** 다른 PC의 연결부(404), 허용되지 않은 승인에 대한 결과(`not_allowed`), 다른 항목의 결과(`item_mismatch`), 두 번째 결과(`result_closed`). 결과 없이 차례가 끝나면 허용한 것은 `unknown`. 결정은 먼저 닿은 하나만 적용(두 화면 동시 응답 → 나머지 409).
- **화면:** 대기 카드는 종류 `approval` 그대로(번호·AI 직원 표시 추가). 결정 뒤에는 **새 종류 `approval_result`**(버튼 없음, 결정 뒤 30분·최근 3장) — 이미 설치된 앱·예전 화면은 모르는 종류라 무시하므로 버튼이 잘못 다시 뜨지 않는다. 웹(`app.html`, PC형·허브형 공용)과 이어온 앱(`app/`)에 같은 글로 넣었다.
- **메신저:** 승인 번호를 서버가 대화마다 매긴다(전에는 메신저 프로그램 메모리 — 다시 켜면 사라졌음). `/허용 n`은 그 대화방에 연결된 대화의 번호로 찾는다. 허용 뒤 실제 결과("승인 요청 n: 실행 완료/실행 실패(종료 코드)/실행 결과를 확인하지 못함")를 같은 대화방에 한 번 알린다.
- **시험:** `tests/pilot/rc1-approval-result.test.mjs` 13건(거부 실행 0·허용 실행 1·중복 응답 1·주인 아닌 사람/다른 PC/만료 차단·실패 두 화면 일치·항목 불일치·결과 불명·번호 유지·메신저 알림). 민감도 17종(중복 결정·거부된 승인의 결과·다른 항목·두 번째 결과·결과 불명·다른 PC·번호·실행 중 표시·항목 ID 없이 잇기·종료 코드·중복 보고·버튼 카드·메신저 알림 등) 모두 잡힘, 전체 353건 중 실패 0.

## 8. RC2 구현 기록 (2026-11-16, 신산님 "RC2 먼저" — RC1 실제 확인은 시험 대화가 데스크톱에 열려 있어 뒤로)

- **API:** `POST /v1/requests/<id>/stop`(웹·앱·메신저·외부 키 공통, 그 대화에 접근할 수 있는 사람만). 대기 중(`queued`) → 바로 취소 200 `cancelled`(연결부에 넘어가지 않음, 세션 잠금 풂). 실행 중(`dispatching`·`running`) → 202 `stopping`, 요청에 멈춤 요청 시각·누가(`stop_requested_at`·`stop_by`)를 남기고 기다리던 승인 카드는 차례 끝으로 거부. 이미 끝난 것 → 409 `not_running`(그때 상태 함께). 사람이 띄운 Claude 채널 창은 실행 중 409 `stop_unsupported`(원래 창에서). 결과 조회에 `stopRequested`.
- **연결부:** 실행하는 동안 2초마다 `GET /v1/device/jobs/<id>/control`(그 PC의 요청만)로 묻고, 멈추라고 하면 엔진에 멈춤 신호(AbortSignal)를 준다. 실행이 끝나면 더 묻지 않는다.
- **엔진별로 "멈춘 것을 확인"하는 방법:** Codex 작업 모드·동시 사용(app-server) → `turn/interrupt`를 보내고 엔진이 차례를 `interrupted`로 끝냈다고 알려 와야 중지됨. Codex 번갈아 쓰기·새 세션(SDK) → SDK 실행을 끊어 codex 프로세스가 끝나고 읽기가 정상 종료돼야 중지됨. Claude 새 세션·Grok·Antigravity(한 번 실행 CLI) → 프로세스를 끝내고 닫힌 것을 확인. 확인하면 `cancelled`(`stopped_by_user`), 신호를 보냈는데 확인하지 못하면 `unknown`(`stop_unconfirmed`, 잠금 유지·자동 재전송 없음). 멈추라고 했어도 엔진이 먼저 답을 끝냈으면 `completed`(먼저 확정된 쪽). 멈추라고 하지 않았는데 중지됐다고 오면 `unknown`(`unexpected_stop`).
- **화면:** 웹(PC형·허브형 공용) 1:1 대화의 진행 표시 옆 **중지** → "멈추는 중…" → "중지됨". 이어온 앱 1:1의 "답을 기다리는 중…" 옆 **중지**(앱은 새 빌드 필요). 방(여러 AI 직원) 화면의 중지 버튼은 RC3 작업 화면과 함께.
- **메신저:** `/stop`·`/중지`(슬랙 `!stop`) — 그 대화방에서 마지막으로 보낸 질문만, 보낸 사람이나 주인만. 시작 전이면 "중지됨", 실행 중이면 "멈추는 중" 뒤 질문을 기다리던 쪽이 "중지됨"을 알림. 답장으로 고르기는 아직(대화방마다 한 번에 한 질문이라 마지막 질문으로 충분 — 필요하면 RC3에서).
- **시험:** `tests/pilot/rc2-request-stop.test.mjs` 12건(대기 중 취소·잠금 풂, 실행 중 멈춤·다른 PC/다른 사람 차단, 확인 못 한 중지·뜻밖의 중지 = 결과 불명, 먼저 끝난 답 우선, Claude 창 거부, 승인 카드 정리, A만 멈추고 B 진행(실제 pollOnce), 감시 종료, app-server interrupt, CLI 프로세스 종료(실제 프로세스), 메신저 /stop 권한·알림). 민감도 17종 모두 잡힘. 전체 365건 중 통과 364·실패 0·건너뜀 1, 앱 타입 검사·시험 22건 통과. 모델 호출 0.
